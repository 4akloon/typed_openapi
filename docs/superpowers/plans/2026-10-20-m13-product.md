# M13 plan: documentation, lint, distribution and 0.1.0 readiness

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `typed_openapi` usable by people who did not write it: reference docs and JSON Schemas generated from the code and kept fresh by CI, a `lint` command for backend teams, release binaries with a GitHub Action, four checked framework recipes, and the four packages ready to publish as 0.1.0 (nothing is tagged or published).

**Architecture:** One catalog per source of truth (diagnostic codes, `x-` extensions, config keys, overrides keys), each read by the code that needs it and by a generator in `typed_openapi_tool` (`bin/docs.dart generate|check`) that writes Markdown and JSON Schema; a test compares each schema with the loader it describes. `lint` is `SpecLinter` in the core (load, normalize, no IR) plus `PresetDetector`, and a thin `LintCommand` in the generator. Distribution is shell scripts (`release/`, `action/`) tested on Linux, a release workflow validated by actionlint, and a release checklist for the manual steps.

**Tech Stack:** Dart 3.10 pub workspace, `package:test`, `package:args`, `package:yaml` (tool tests only), bash, GitHub Actions, `rhysd/actionlint` (Docker image, CI only), `dart compile exe`.

**Spec:** [2026-10-13-m13-product-design.md](../specs/2026-10-13-m13-product-design.md) (eight decisions; each task names the decision it implements). Brief: [m13-plan.md](../briefs/m13-plan.md).

## Review Focus

Failure modes the spec implies that no unit test of a single task targets; each says where it is pinned.

1. **A lint report tells a backend team to write a Dart override.** Pinned in Task 8: a test runs every format against every preset (and the whole `DiagnosticCode` hint table through `Diagnostic.forBackend`) and asserts the word "override" never appears in a fix or hint.
2. **A JSON Schema drifts from the loader** (a key is added to a reader, not to the catalog; a schema says valid what the loader rejects). Pinned in Tasks 3 and 4: one case table per catalog is judged by both the schema and the loader, and `ConfigKeys`/`OverrideKeys` are derived from the catalog so a reader cannot allow a key the schema lacks; Task 6 pins that the published files equal what the generator writes.
3. **A generated doc goes stale and nobody notices.** Pinned in Task 6: `docs.dart check` is a test (`the generated docs of the repository are current`) and a CI job; a doc comment without `Example:` or `Fix:` fails the same test (Task 5).
4. **The detector tailors advice to the wrong framework, or throws on a malformed spec.** Pinned in Task 7: two frameworks' marks give generic, wrong types give no mark, an operation id that only looks like Nest's is not Nest's; Task 9 pins every corpus spec against the framework `corpus.yaml` names.
5. **A value from a workflow or a spec reaches a shell as code** (the action's `spec` input, the release version). Pinned in Task 13: `run.sh` passes a spec path with spaces and `;` as one word, `install.sh` refuses `0.1.0/../x`, every workflow input reaches a script through `env:`.
6. **The docs claim more than the repository shows** (a support-matrix row without a proof, a recipe without a source, a broken link, "available on pub.dev" before it is). Pinned in Tasks 11, 12 and 14: tests for proofs, `Sources`, links, and the grep step of the release checklist.

## Decisions taken

The spec's eight decisions are applied as written. These points the spec leaves open are settled here (also listed under "Open questions"):

- **Lint runs the stages that read the spec** (loader, version, normalizer with every rule) and builds no IR. Codes that only the IR stage reports (TOA453, TOA553, TOA651 ...) belong to `check`, which needs a config.
- **`Diagnostic.backendFix`**: a rule that offers a step in the overrides file also gives the same advice without that step; `forBackend()` prints the source step, or the fix when it names no override, else nothing.
- **Catalog shape**: `KeySpec` (name, `KeyType`, description, example, default, required, invalid examples) in `lib/src/schema/`; `ConfigKeys` and `OverrideKeys` (what the loaders allow) are derived from the catalogs.
- **Registry shape**: `SpecExtension` (key, applies to, effect, example, diagnostics) in `lib/src/extensions/`; a test fails when `lib/` writes an `x-` literal anywhere else.
- **Doc comment convention** for `DiagnosticCode`: meaning paragraph(s), then `Example:` and `Fix:` paragraphs, each ending with a full stop. The catalog `doc/diagnostics.md` is generated from them.
- **Tags and archives**: release tag `typed_openapi-v<version>` (the tag `publish.yml` already uses); every target is a `.tar.gz`, Windows included; the action takes a required `version` or an `executable`, never "latest".
- **Pre-release headings**: CHANGELOGs say `## 0.1.0 - Unreleased` until the release (the semver rule reads that heading); the checklist drops ` - Unreleased`.
