# M6: семантична IR і Dart-мапінг — дизайн

Дата: 2026-10-12. Вимоги: R4 (вибір того, що генерувати), R5 (іменування), R6.1–R6.4, R6.8 (модель даних, власні типи), R7.2 (правило тристановості) ([requirements.md](../../requirements.md)). Дослідження: [research/README](../../research/README.md) §7 (архітектура: normalize → overrides → resolve → dispatch → naming → незмінна IR → Dart-мапінг), [research/07](../../research/07-dart-building-blocks.md). Вхід — `NormalizedSpec` з M3/M4 (модель після override-ів і правил, з `OverrideSet`). Вихід — незмінна IR, з якої M8 (моделі) і M9 (операції) генерують код. Runtime-типи — з M7.

## Рішення

1. **IR незалежна від Dart-синтаксису, але вже з Dart-іменами й типами.** Два шари: семантична IR (моделі, поля, enum, union, операції, параметри, тіла, відповіді, групи) і Dart-мапінг (імена ідентифікаторів, типи полів). Емітери M8/M9 лише друкують. IR повністю детермінована (R13.1) і незмінна.
2. **Іменування за вимогами R5, без евристик.**
   - Методи: `operationId` у lowerCamelCase; без `operationId` — з методу і шляху. Трансформації (regex-префікс, суфікс версії) — лише з конфігу або пресету; пресет `nestjs` зрізає `XController_`.
   - Схеми: ім'я як у специфікації (PascalCase-ідентифікатор; `Dto` не зрізається). Властивості: lowerCamelCase, JSON-ключ зберігається як є.
   - Inline-схеми й inline-enum: `<Parent><Property>` (R5.4); однакові набори значень enum дедуплікуються.
   - Групи: клас на тег, шаблон `{Tag}Api` (налаштовується), операція з кількома тегами — у першій групі (info), без тегу — `DefaultApi`; нормалізація тегів; стратегії `group_by: tag|path|single` (R5.3).
3. **Колізії — суфікс плюс діагностика (рішення користувача).** Ім'я, що збігається із зарезервованим словом Dart або іменем із `dart:core`, отримує детермінований суфікс: схема `List` → `ListModel`, властивість `class` → `class_`; JSON-ключ не змінюється. Інші колізії (однакові імена після нормалізації, path і query з одним іменем, дві схеми з одним іменем) — так само детерміновано, з info-діагностикою і готовим override-ом `name`.
4. **Моделі за напрямком — лише коли треба (рішення користувача).** Якщо схема має `readOnly` або `writeOnly` властивості і використовується і в запитах, і у відповідях, генеруються дві моделі: `Pet` (відповідь: readOnly поля присутні, writeOnly — відсутні) і `PetInput` (запит: без readOnly, з writeOnly). Суфікс налаштовується, ім'я — через override `name`. Схеми без readOnly/writeOnly — одна модель.
5. **Матриця required × nullable (R6.1).** Відповідь: required+non-null → `T`; required+nullable → `T?`; optional → `T?` (відсутнє і `null` дають `null`, рішення M7). Запит: required → обов'язковий параметр конструктора; optional → `T?`, `null` не надсилається (R7.3); поле за правилом тристановості — `Patch<T>?` (R7.1).
6. **Правило тристановості (R7.2):** за замовчуванням — optional + nullable властивість у тілі PATCH. Альтернативи в конфігу: будь-яке optional, `x-`-розширення; override `triState` на полі має пріоритет.
7. **Типи і формати (R6.2, рішення користувача).** `integer` → `int` (зокрема `int64`; у вебі точність до 2^53 — задокументувати, обхід — override на `String`); `number` + `float`/`double` → `double`; `number` без формату → `num`; `string` → `String`; `date-time` → `DateTime` (UTC); `date` → `Date` з runtime (додається в M7); `byte` → `Uint8List` (base64); `binary` → байти/стрім (уточнюється в M9 для тіл); `uuid`, `email`, `uri` → `String`; `boolean` → `bool`; довільний JSON (`{}`, без типу) → `JsonValue`; `additionalProperties` → `Map<String, T>`; масиви — `List<T>`. Глобальний мапінг `types:` і власні типи `types.formats` / `types.schemas` / override `dartType` (R6.8) мають пріоритет.
8. **Інтерпретаційні правила, перенесені з M3:** `allOf` з одним `$ref` (зокрема nullable) — посилання на тип; кілька частин — плоска модель (R6.3); `anyOf`/`oneOf` з однією не-null гілкою плюс null — nullable тип цієї гілки; `const` — enum з одним значенням; конверт `{data: T}` з єдиною обов'язковою властивістю `data` розгортається (R6.4), альтернатива в конфігу — дженерик-обгортка; схеми з `data` і іншими полями — звичайні моделі.
9. **Union-и (`oneOf`/`anyOf` з кількома не-null гілками) — вузол IR уже в M6:** варіанти, дискримінатор і `mapping` (розв'язаний), вичерпність (`exhaustive`, override `exhaustive: false`). Код для них — M8 (R9).
10. **Фільтри і tree-shaking (R4.1, R4.2):** include/exclude за тегами, `operationId` і glob шляхів у конфігу клієнта; поле генерації `exclude` з override-ів; генеруються лише схеми, досяжні з вибраних операцій. Конфлікт фільтрів — діагностика.
11. **Поля генерації з override-ів (M4) споживаються тут:** `name`, `exclude`, `exhaustive`, `group`, `dartType`, `triState`. Записи, які M4 не застосував (TOA804/805/806), не впливають на IR.
12. **Нічого не вгадується:** кожне рішення мапінгу, яке не випливає однозначно зі схеми, — діагностика з готовим override-ом (R2.5).

## Що не входить

- Генерація коду (M8 — моделі, M9 — операції і `generate`).
- Union-и в коді, SSE-події (M8, M10).
- Вкладені групи (OAS 3.2 `tag.parent`) — пізніше.
