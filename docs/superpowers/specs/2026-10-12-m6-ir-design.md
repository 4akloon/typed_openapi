# M6: semantic IR and Dart mapping — design

Date: 2026-10-12. Requirements: R4 (choice of what to generate), R5 (naming), R6.1–R6.4, R6.8 (data model, custom types), R7.2 (tri-state rule) ([requirements.md](../../requirements.md)). Research: [research/README](../../research/README.md) §7 (architecture: normalize → overrides → resolve → dispatch → naming → immutable IR → Dart mapping), [research/07](../../research/07-dart-building-blocks.md). Input — `NormalizedSpec` from M3/M4 (the model after overrides and rules, with `OverrideSet`). Output — an immutable IR, from which M8 (models) and M9 (operations) generate code. Runtime types — from M7.

## Decisions

1. **The IR is independent of Dart syntax, but already has Dart names and types.** Two layers: the semantic IR (models, fields, enums, unions, operations, parameters, bodies, responses, groups) and the Dart mapping (identifier names, field types). The M8/M9 emitters only print. The IR is fully deterministic (R13.1) and immutable.
2. **Naming per the R5 requirements, without heuristics.**
   - Methods: `operationId` in lowerCamelCase; without `operationId` — from the method and the path. Transformations (a regex prefix, a version suffix) — only from the config or a preset; the `nestjs` preset strips `XController_`.
   - Schemas: the name as in the spec (a PascalCase identifier; `Dto` is not stripped). Properties: lowerCamelCase, the JSON key is kept as is.
   - Inline schemas and inline enums: `<Parent><Property>` (R5.4); identical sets of enum values are deduplicated.
   - Groups: a class per tag, template `{Tag}Api` (configurable); an operation with several tags — in the first group (info); without a tag — `DefaultApi`; normalization of tags; strategies `group_by: tag|path|single` (R5.3).
3. **Collisions — a suffix plus a diagnostic (user decision).** A name that matches a reserved Dart word or a name from `dart:core` gets a deterministic suffix: a schema `List` → `ListModel`, a property `class` → `class_`; the JSON key does not change. Other collisions (identical names after normalization, a path and a query parameter with one name, two schemas with one name) — likewise deterministic, with an info diagnostic and a ready `name` override.
4. **Models by direction — only when needed (user decision).** If a schema has `readOnly` or `writeOnly` properties and is used both in requests and in responses, two models are generated: `Pet` (response: readOnly fields are present, writeOnly — absent) and `PetInput` (request: without readOnly, with writeOnly). The suffix is configurable; the name — through the `name` override. Schemas without readOnly/writeOnly — one model.
5. **Matrix of required × nullable (R6.1).** Response: required+non-null → `T`; required+nullable → `T?`; optional → `T?` (absent and `null` both give `null`, M7 decision). Request: required → a required constructor parameter; optional → `T?`, `null` is not sent (R7.3); a field under the tri-state rule — `Patch<T>?` (R7.1).
6. **Tri-state rule (R7.2):** by default — an optional + nullable property in a PATCH body. Alternatives in the config: any optional property, `x-` extensions; the `triState` override on a field takes precedence.
7. **Types and formats (R6.2, user decision).** `integer` → `int` (including `int64`; on the web the precision up to 2^53 is to be documented, the workaround — a `String` override); `number` + `float`/`double` → `double`; `number` without a format → `num`; `string` → `String`; `date-time` → `DateTime` (UTC); `date` → `Date` from the runtime (added in M7); `byte` → `Uint8List` (base64); `binary` → bytes/stream (specified in M9 for bodies); `uuid`, `email`, `uri` → `String`; `boolean` → `bool`; arbitrary JSON (`{}`, without a type) → `JsonValue`; `additionalProperties` → `Map<String, T>`; arrays — `List<T>`. The global `types:` mapping and custom types `types.formats` / `types.schemas` / the `dartType` override (R6.8) take precedence.
8. **Interpretation rules moved from M3:** `allOf` with one `$ref` (including nullable) — a reference to the type; several parts — a flat model (R6.3); `anyOf`/`oneOf` with one non-null branch plus null — the nullable type of that branch; `const` — an enum with one value; the envelope `{data: T}` with the single required property `data` is unwrapped (R6.4), the alternative in the config — a generic wrapper; schemas with `data` and other fields — ordinary models.
9. **Unions (`oneOf`/`anyOf` with several non-null branches) — an IR node already in M6:** variants, discriminator and `mapping` (resolved), exhaustiveness (`exhaustive`, the `exhaustive: false` override). The code for them — M8 (R9).
10. **Filters and tree-shaking (R4.1, R4.2):** include/exclude by tags, `operationId` and path globs in the client config; the generation field `exclude` from overrides; only schemas reachable from the selected operations are generated. A conflict of filters — a diagnostic.
11. **Generation fields from overrides (M4) are consumed here:** `name`, `exclude`, `exhaustive`, `group`, `dartType`, `triState`. Entries that M4 did not apply (TOA804/805/806) do not affect the IR.
12. **Nothing is guessed:** every mapping decision that does not follow unambiguously from the schema is a diagnostic with a ready override (R2.5).

## Out of scope

- Code generation (M8 — models, M9 — operations and `generate`).
- Unions in code, SSE events (M8, M10).
- Nested groups (OAS 3.2 `tag.parent`) — later.
