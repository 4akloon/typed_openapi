# M11: corpus, golden tests, platform matrix, escaping fuzz — design

**Date:** 2026-10-13.

**Requirements:** R15.3 (golden tests; the public specs Petstore, Stripe, GitHub, OpenAI and Kubernetes compile and pass the analyzer; runtime decoding tests) and R15.4 (semver: a change of output for the same input is a breaking change). See [requirements.md](../../requirements.md).

**Roadmap:** row M11, and every row parked with the target "M11" in [roadmap.md](../../roadmap.md).

**Earlier stages:** M8–M10 checked the corpus, the fuzz and the analyzer by hand during reviews, from scripts in a scratchpad. M11 moves these checks into the repository and CI.

The user made these decisions in a grilling session.

## Decisions

### 1. Where the specs come from

The repository keeps only a pinned list, `corpus.yaml`, and never the specs themselves. Each entry holds:
- the spec's URL, fixed to a commit or a tag;
- the file's sha256;
- its license;
- the expectation from decision 6.

A tool, `tool/corpus fetch`, downloads the files into a cache and verifies every hash. A mismatch is an error.

The corpus runs as its own CI job, with a cache. The regular `dart test` of both packages stays offline, as the repo rule requires.

### 2. Fixing the output: `corpus.lock`

The repository keeps `corpus.lock`. For each client it records:
- the sha256 of the whole output and of each file;
- the count of diagnostics by code.

CI fails on any difference and lists the changed files and codes. A change of output is a deliberate act: `tool/corpus update` rewrites the lock, and the new lock goes in the same commit as the change that caused it.

Full golden files remain only for the small fixtures (petstore, chat and the like).

### 3. Runtime decoding tests (R15.3)

Every value from two sources is checked on the generated clients of the corpus:
- the `example` and `examples` of responses and schemas in the spec itself;
- synthetic values the tool builds from a schema: the required fields, every union variant and the boundaries of enums.

Each value goes through `fromJson` → `toJson` → `fromJson`, and the second result must equal the first.

An example that does not match its own schema is a defect of the spec, not of the generator. It is counted in `corpus.lock` and does not fail the test.

### 4. The platform and SDK matrix, in layers

- **Every PR:**
  - ubuntu × SDK 3.10 (the minimum) and stable, with the full test suites;
  - the runtime also in Chrome, on dart2js and on dart2wasm;
  - one test run on macOS and one on Windows, with the stable SDK.
- **Corpus (every PR):** ubuntu × SDK 3.10 and stable. It checks four things:
  - `generate`, then `dart analyze --fatal-infos` on the output;
  - a second `generate` writes no file;
  - the lock comparison;
  - `dart format --set-exit-if-changed` with the formatter of both SDKs on the generated code. The generated code carries `// dart format off`, so this must pass.
- **Nightly:**
  - SDK beta, where a failure is a warning only;
  - the corpus on Windows.

### 5. The escaping fuzz

The fuzz harness moves into the repository as `tool/fuzz`, with seeds. A quick run of about 200 seeds goes on every PR, and a run of 6000 seeds nightly.

It puts hostile strings at every sink a spec string reaches:
- names;
- descriptions;
- enum values;
- property keys;
- status keys;
- media types;
- event names.

It checks three things:
1. The generated code passes the analyzer.
2. At run time, every string literal equals the spec string it came from, so escaping never changes content.
3. Spec text stays inside its sink: a doc comment never leaves its comment, and the reports contain no raw control characters.

A seed that found a defect becomes a permanent fixture.

### 6. The corpus set

- The 5 specs R15.3 requires: Petstore, Stripe, GitHub, OpenAI and Kubernetes.
- The 14 public specs used in M8–M10.
- 3–4 public code-first specs from open projects: one each generated by NestJS, FastAPI, Spring (springdoc) and ASP.NET (Swashbuckle).

The private company spec is never used.

Each entry states its expectation. There are two:
- `generate`: the client generates and passes the analyzer.
- `check-errors: [TOA…]`: generation skips the client for the listed errors of the spec itself, as with artemis and TOA009.

### 7. Semver (R15.4)

`tool/corpus check` compares a PR with its base branch. When the output changed, in `corpus.lock` or in a fixture's golden files, the PR must contain two things:
- an entry in the generator's CHANGELOG under "Output changes", naming the clients and files affected;
- a raised version: minor before 1.0, major after it.

Without both, CI fails, and the message says what to add.

### 8. The rows parked for M11

Every roadmap row with the target M11 is checked by a test on the matrix platform it concerns. It is then either fixed, or recorded as a documented limitation. The rows:
- Windows paths with a drive letter;
- the SARIF result shapes, checked offline against the SARIF 2.1.0 JSON schema and GitHub's ingestion rules, with no real upload to code scanning;
- whether the browser really drops the `Cookie` header;
- `1.0` in a parameter on dart2js;
- `style: cookie`;
- NaN in `DeepEquality` on dart2js;
- case and hard-link behaviour on Linux and Windows.

## Out of scope

- Real uploads to GitHub code scanning.
- `diff` between regenerations with change categories. That is M12; M11 only detects that output changed.
- Publishing the corpus specs or the generated clients.
