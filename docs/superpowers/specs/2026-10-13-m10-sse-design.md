# M10: server-sent events — design

**Date:** 2026-10-13.

**Requirements:** R12.1, R12.2, R12.4, R12.5. R12.6 (NDJSON/JSONL) is deferred. See [requirements.md](../../requirements.md).

**Earlier stages this builds on:**
- [M7 design](2026-10-12-m7-runtime-design.md), decisions 16–18:
  - the WHATWG decoder `SseDecoder`;
  - `DioRequestSender.openEvents` returning `Result<Stream<SseItem<T>>, E>`, where `SseItem` is `SseEvent` | `SseDecodeError` | `SseDisconnected`;
  - a stream that never emits errors;
  - the web limitation with Dio's default browser adapter.
- [M9 design](2026-10-13-m9-operations-design.md). Event-stream operations are not generated there (TOA654).
- [M4 design](2026-10-12-m4-overrides-design.md). The `sse` generation field was deferred until this stage settled its shape.

The decisions below were made with the user in a grilling session.

## Decisions

1. **What the schema of a `text/event-stream` response means.**
   - `itemSchema` (OAS 3.2) describes the whole event: `{event, data, id, retry}`.
     - When `data` has `contentMediaType: application/json` and a `contentSchema`, the event data type `T` is that `contentSchema`.
     - When `data` is a plain string, `T` is `String`.
   - `schema` is the older code-first practice (NestJS, FastAPI, Spring). It describes the JSON inside `data`.
     - When `schema` is an array, its item type is taken as the event type, and an info diagnostic explains this.
   - The `sse` override wins over both.
2. **Event typing.**
   - When the spec types each event separately, the stream item is a sealed union keyed by the SSE `event` field, not by the JSON. The spec does this through an `itemSchema` `oneOf` whose branches have `event: {const: …}`, or through the override's `sse.events`.
     - Example: `ChatEvent` → `ChatEventDelta(Delta)`, `ChatEventUsage(Usage)`, `ChatEventDone()`, `ChatEventUnknown(event, data)`.
     - The shape is the same as M8 unions, and switches over it are exhaustive. The unknown variant is R12.2.
     - The names are claimed in the operations' scope after models, as in M9.
   - Otherwise there is one type `T` for all events, and the event name stays available as `SseEvent.event`.
3. **Reconnection (R12.5) is off by default.**
   - It is enabled per call through `CallOptions` (`SseOptions(reconnect: …)`), or per operation through config or the `sse.reconnect` override.
   - A POST operation reconnects only when reconnection is enabled for the operation. A per-call request on a POST has no effect, and a diagnostic says how to enable it.
   - On reconnect the runtime sends `Last-Event-ID`.
   - The first delay is the server's `retry`, or 1 s when the server sent none. Each further delay doubles, up to 30 s, with at most 5 attempts. All of these values can be configured through `SseOptions`.
4. **Reconnection is visible in the stream.** A new item `SseReconnecting(attempt, delay, cause)` arrives before each attempt. `SseDisconnected` stays the last item, emitted after the attempts run out or when reconnection is off. The stream still emits no errors.
5. **An operation that offers both JSON and `text/event-stream`, for example OpenAI `createChatCompletion`, gets two methods:**
   - `createChatCompletion(...)` sends `Accept: application/json` and returns `Result<T, E>`.
   - `createChatCompletionStream(...)` sends `Accept: text/event-stream` and returns `Result<Stream<SseItem<…>>, E>`.
   - The suffix is configurable through `naming.stream_suffix`, and the name can be set by override. An info diagnostic reports the second method.
   - Fields such as a `stream: true` flag in the body are left to the user; the generator does not guess them.
6. **The `sse` override, on an operation addressed by `operationId` or `METHOD /path`:**
   ```yaml
   sse:
     data: ChatCompletionChunk   # one type for all events (a components.schemas key or an inline schema)
     events:                     # instead of data: a union by event name; null = an event without data
       delta: ChatDelta
       done: null
     unknown: keep | ignore      # unknown events: the Unknown variant (default) or dropped
     reconnect: true             # reconnection for this operation (POST only this way)
     method: stream | only | none  # beside the JSON method / instead of it / no SSE method
   ```
   - Keys are camelCase, like other overrides.
   - `data` together with `events` is an error.
   - An unknown key is TOA803, with "did you mean".
7. **Method signature.** An event-stream method has the same shape as other M9 methods: named parameters, `body:`, and `CallOptions? call`. It returns `Future<Result<Stream<SseItem<T>>, E>>`.
   - The stream opens only for documented success statuses (M7). Other statuses decode like any response: `HttpError`, `UndocumentedStatus`, `DecodeError`.
   - An event that fails to decode becomes `SseDecodeError`, and the stream goes on.
8. **Web.** With Dio's default browser adapter, a stream method returns `TransportError` that explains how to plug a fetch-based adapter into your own Dio (M7). Nothing more is needed in M10.
9. **Diagnostics.** TOA654 ("event-stream operation not generated") stays only for shapes M10 still cannot express. Any new codes go in the 6xx media-type range; the plan fixes the numbers.

## Out of scope

- NDJSON / JSONL streams (R12.6).
- WebSockets.
- Webhooks and callbacks.
