# M4: override-и — дизайн

Дата: 2026-10-12. Вимоги: R3.1, R3.2 ([requirements.md](../../requirements.md)); R3.3 (Overlay, JSON Patch) — поза M4. Дослідження: [research/06 §B](../../research/06-spec-versions-and-defects.md), [research/README](../../research/README.md) (R3: обов'язковий `reason` у Stainless, діагностика «override не знайшов цілі», override-и логічні, а не за згенерованими іменами). Попередній етап: [дизайн M3](2026-10-11-m3-normalizer-design.md).

## Рішення

1. **Свій логічний формат.** Файл `typed_openapi.overrides.yaml` (шлях — `clients.<name>.overrides` у конфігу, JSON або YAML, читається компоновщиком M3). Ціль адресується сутністю специфікації, а не JSON-pointer-ом і не згенерованим ім'ям: операція — за `operationId` або `METHOD /path`, схема — за ключем у `components.schemas`, властивість, параметр, відповідь — вкладено в них. Overlay 1.2 і JSON Patch (R3.3) — окремим етапом пізніше.
2. **M4 читає і перевіряє весь файл, але застосовує лише поля специфікації.**
   - Поля специфікації (`type`, `format`, `nullable`, `required`, `items`, `additionalProperties`, `enum`, `discriminator`, схема як `$ref`, схема відповіді, content-type тіла, `required`/`schema` параметра) стають правками сирого дерева (`SpecEdit`) і застосовуються рушієм правок M3.
   - Поля генерації (`name`, `exclude`, `exhaustive`, `group`, Dart-тип R6.8 `{type, import, converter}`, схеми SSE-подій, режим тристановості) перевіряються і зберігаються в типізованій моделі override-ів, яку отримають M6+. У M4 вони нічого не змінюють.
3. **Override-и — до правил нормалізатора.** Порядок: читання → override-и (правки, перечитування) → проходи нормалізатора. Правила бачать уже виправлену специфікацію, тож дефект, закритий override-ом, не звучить.
4. **Значення override-у замінює значення специфікації** (семантика «set»): список замінює список, скаляр — скаляр; мапа override-у застосовується поле за полем (кожне перелічене поле замінюється, неперелічені лишаються). Злиття списків, як у Overlay, немає.
5. **`nullable` в override-і — абстрактний.** Застосування враховує діалект документа: у 3.0 — `nullable: true`, у 3.1+ — `null` у `type`.
6. **R3.2.** Ціль не знайдено — warning, решта override-ів застосовується. Override нічого не змінив (специфікація вже має це значення) — info «override можна прибрати». Обидва звіти — на позиції override-у у файлі override-ів, з `reason`, якщо він є.
7. **`reason` необов'язковий**, але друкується в діагностиці про override (застарілий, зайвий, конфліктний).
8. **Неоднозначна або конфліктна адресація — помилка override-у, не вгадування.** `operationId`, що трапляється двічі; два записи на ту саму ціль (`getPet` і `GET /pets/{id}`); параметр, ім'я якого неоднозначне між `in` — діагностика з підказкою, як уточнити адресу.
9. **Підказки правил M3 отримують готовий фрагмент override-у.** Правило, яке лише діагностує (подвійний масив, `format` на масиві, object + binary, nullable-enum через `oneOf`, масив без `items`, суперечливий `type`, параметр поза шаблоном тощо), додає до `fix` YAML-фрагмент, який можна скопіювати у файл override-ів. Адреса фрагмента обчислюється з місця діагностики; якщо місце не має логічної адреси, фрагмента немає.
10. **Коди — діапазон 8xx** (TOA800 уже зайнятий «правка не застосована»): невалідний файл override-ів, ціль не знайдено, override нічого не змінив, неоднозначна ціль, конфлікт двох override-ів. Конкретні номери — у плані.

## Що не входить

- Overlay 1.2, JSON Patch (R3.3).
- Споживання полів генерації — M6 і далі.
- Baseline і перевизначення рівнів — M5.
