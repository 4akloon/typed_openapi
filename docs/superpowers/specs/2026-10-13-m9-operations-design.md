# M9: емітер операцій і `generate` — дизайн

**Дата:** 2026-10-13.

**Вимоги:** R5.3, R10.1–R10.9, R11.1–R11.7 ([requirements.md](../../requirements.md)).

**Попередні етапи:**
- [дизайн M6](2026-10-12-m6-ir-design.md) — IR операцій: групи, параметри, тіла, відповіді, `ErrorsIr`;
- [дизайн M7](2026-10-12-m7-runtime-design.md) — `Result`, `CallOptions`, `OperationRequest`, `DioRequestSender`, кодеки параметрів;
- [дизайн M8](2026-10-12-m8-models-design.md) — емітер моделей, `DartWriter`, `generate`, маніфест.

**Перенесено:** [roadmap](../../roadmap.md), розділи «Перенесено з M2–M8» з позначкою M9.

## Рішення

1. **Лише `Result`, без винятків** (рішення 4 research, M7).
   - Кожен метод повертає `Future<Result<T, E>>`.
   - `E = Never`, коли помилок не задокументовано.
   - `T = void`, коли успішна відповідь не має тіла.
2. **Сигнатура методу (рішення користувача).**
   - Усі параметри іменовані, обов'язкові — `required`. Тіло — окремий іменований `body:`. Останнім іде `CallOptions? call`.
   - Приклад: `Future<Result<Pet, UpdatePetError>> updatePet({required String petId, String? traceId, required PetInput body, CallOptions? call})`.
   - Новий параметр у специфікації не зсуває позицій.
   - Імена аргументів беруться з IR (M6). Колізії вже розв'язано там.
3. **Групи і кореневий клієнт (рішення користувача).**
   - Клас на групу `{Tag}Api` (M6, R5.3). Це звичайний клас без модифікаторів, бо його мокають через `implements` (R10.7).
   - Конструктор групи — `PetsApi(Dio dio)`.
   - Кореневий клас називається за іменем клієнта з конфігу: `clients.petstore` → `PetstoreClient(Dio dio)`. Перевизначити можна через `naming.client`. Групи в ньому — поля: `client.pets.getPet(...)`.
   - Генератор не змінює `Dio` користувача (R10.1): ні `baseUrl`, ні інтерсепторів.
4. **Файли (рішення M8, нотатка рев'ю M8 для M9).**
   - API пишеться в `<output>/api/` (`pets_api.dart`, барель `api.dart`), корінь — у `<output>/<client>.dart`.
   - Імена файлів і типів операцій виділяються після моделей у власному просторі імен, тож моделі ніколи не переїжджають.
   - Маніфест і запобіжники M8 діють на всю теку.
5. **Відповіді (R10.6).**
   - Одна успішна відповідь дає `T`. Кілька різних 2xx дають sealed-тип з варіантами за назвою статусу: `CreatePetResponse` → `CreatePetResponseOk` / `…Created` (рішення 18 M8).
   - 204 і відповідь без тіла дають `void`.
   - Статус і заголовки доступні в `Success` (M7).
   - Не-JSON відповіді:
     - `text/*` → `String`;
     - бінарні → `Uint8List`;
     - SSE — M10.
   - Бінарна або текстова успішна відповідь із JSON-помилками має прямий засіб декодування. Це закриває пункт «Перенесено з M7».
6. **Помилки (R11.1, R11.3–R11.5).**
   - `ErrorsIr` з M6:
     - `NoErrors` → `Never`;
     - `SingleError` → тип схеми;
     - `ErrorsByStatus` → sealed `CreatePetError` з варіантами за назвою статусу (рішення 18 M8).
   - Незадокументований статус дає `UndocumentedStatus`, транспорт — `TransportError`, скасування — `Cancelled` (M7).
   - Порожній `statuses` у `SingleError` означає «усі 4xx/5xx» (M6, перенесене).
   - Операція, єдина відповідь якої `default` з тілом, отримує явне правило: діагностику й тип успіху `void` або `JsonValue`. Конкретне правило визначає план.
7. **Тіла запиту (R10.4).**
   - JSON — модель.
   - `application/x-www-form-urlencoded` — модель, кодується runtime-ом з `encoding` (`style` і `explode` для кожної властивості). Сюди переходить `encoding` медіатипу, перенесений з M6 в IR.
   - `multipart/form-data` — модель частин.
   - Бінарне тіло.
8. **Файли — свій тип у runtime (рішення користувача).**
   - Тип: `FileUpload.bytes(Uint8List, {filename, contentType})` і `FileUpload.stream(Stream<List<int>>, {length, filename, contentType})`.
   - Runtime перетворює його на `MultipartFile` або тіло Dio. Dio-типи не потрапляють у сигнатури згенерованих методів.
   - Працює на вебі (bytes).
9. **Параметри (R10.3)** кодуються runtime-ом (M7).
   - `querystring` (OAS 3.2) переходить у runtime як окремий параметр «весь query», якщо це вкладається в план. Інакше лишається TOA564.
   - Шаблон змінної шляху має одне визначення на генератор і runtime (перенесене з M6).
10. **Security і servers (R10.8, R10.9).**
    - `securitySchemes` і `security` операції потрапляють у `OperationInfo.security` як метадані для інтерсепторів. Самі ключі генератор не підставляє.
    - `servers` генеруються як константи кореневого клієнта: URL-шаблони і змінні з типобезпечною підстановкою. Встановлювати їх у Dio — справа користувача (R10.1).
11. **Конверт `{data: T}`** лише розгортається (рішення M6). Дженерик-режим (`ApiData<T>`) не робимо в M9 (рішення користувача). У roadmap — «коли знадобиться».
12. **Імпорти.**
    - Згенерований API імпортує `package:dio` і runtime через `show`.
    - Імена, які вони експортують і які можуть зіткнутися зі схемами (`Response`, `Options`, `Headers`), розв'язуються одним способом: або `show` без конфліктних імен, або резервування в IR. Вибір фіксує план (перенесене з M6).
13. **`generate` пише весь клієнт**: моделі, API і корінь. Пропуск клієнтів із помилками, маніфест, `--force` і блокування діють як у M8.
14. **Діагностики.**
    - TOA561 (байти проти відкинутих альтернатив) розділяється на два коди.
    - Нумерація медіатипів і помилок узгоджується з 6xx, поки коди не опубліковано (перенесене з M6).

## Що не входить

- SSE-методи — M10.
- `callbacks`, `links`, вебхуки — пізніше. План вирішує, чи потрібна діагностика «не генерується».
- Дженерик-конверт.
- HTTP-абстракція поза Dio — до 1.0.
