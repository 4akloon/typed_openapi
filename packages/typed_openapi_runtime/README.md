# typed_openapi_runtime

Runtime support for clients generated by
[`typed_openapi`](https://pub.dev/packages/typed_openapi): the only package generated
code depends on. Dependencies: `dio` and `meta`.

> **Status:** in development, not published yet.

## Contents

- `Result<T, E>`: every generated method returns one; nothing is thrown for
  expected problems. Read it with pattern matching:

  ```dart
  switch (await api.pets.getPetById(petId: 1)) {
    case Success(:final data): show(data);
    case HttpError(:final body): showError(body);          // documented 4xx/5xx
    case DecodeError(:final error): log(error.pointer);    // body does not match
    case UndocumentedStatus() || TransportError() || Cancelled(): retryLater();
  }
  ```

  An operation without documented errors has `E = Never`. A `switch` over
  it still needs `case Failure()` (which covers every failure), or else a
  case for every failure variant including `HttpError()`, because the other
  failures (transport, cancel, decode, undocumented status) are still
  possible; `HttpError()` alone is not enough. An operation without a
  response body has `T = void`: match it with `Success()`.

- `Patch<T>` for three-state request fields: a `Patch<T>?` field that is
  `null` is not sent, `.nullValue()` sends `null`, `.value(x)` sends `x`.
- `JsonReader` for generated `fromJson`: strict decoding (the only widening
  is an integer where a number is expected) that throws
  `JsonDecodeException` with the JSON pointer, the expected and the actual
  JSON type of the first mismatch. `JsonValue` holds any JSON value.
- `Date` for `format: date` (`YYYY-MM-DD`, no time or time zone), read with
  `JsonReader.asDate` and written with `Date.toJson()`; `Date.parse` throws a
  `FormatException`, `Date.tryParse` returns `null`.
- For generated models: `DeepEquality` (deep `==` and `hashCode` of lists,
  maps and patches), `JsonReader.constant`, `additional` (the keys a model
  does not list, as an unmodifiable map) and `asBytes`, and `immutable`
  re-exported from `package:meta`, so generated code imports only this
  package.
- Parameter encoders for the OpenAPI styles (`simple`, `label`, `matrix`,
  `form`, `spaceDelimited`, `pipeDelimited`, `deepObject`, headers,
  cookies) with RFC 3986 percent-encoding.
- `DioRequestSender`: sends a request through your `Dio` and types the
  outcome. `CallOptions` carries the per-call cancel token, headers,
  `extra` and progress callbacks. Headers in `CallOptions.headers` win over
  the operation's header parameters, but not over its `Content-Type`: the
  content type of the request body (`application/json`, for example) always
  wins, so a `Content-Type` given there is ignored when the operation
  sends a body.
- An event stream (`text/event-stream`) decoder following WHATWG;
  `DioRequestSender.openEvents` returns a `Result` whose `Success` holds a
  stream of `SseEvent`, `SseDecodeError` (one bad event) and, last,
  `SseDisconnected`. Problems with the data are items, never stream errors
  (one exception: an `Error` thrown by your event decoder is a bug, so it
  reaches the listener as a stream error and the stream closes). Listen to
  the stream or cancel it: an unlistened stream keeps the connection open.
  Cancelling the subscription cancels the request.
- Reconnection is off by default. A call turns it on with
  `CallOptions(sse: SseOptions(reconnect: true))`; an operation can enable
  it for every call (the `sse.reconnect` override or config key of the
  generator), and then `reconnect: false` in the call turns it off. A GET
  can reconnect when the call asks; any other method only when its operation
  enables it, since repeating the request may not be safe. When a
  connection ends, the stream emits `SseReconnecting` (the attempt, the
  delay and why), waits, and opens the request again with the last event id
  as `Last-Event-ID` (an id that is not printable ASCII is not sent). The
  wait is the server's `retry`, else 1 s, doubling to a cap of 30 s (a
  server `retry` over the cap is kept). After 5 attempts in a row that bring
  no message the stream ends; a message on a new connection (an event, also
  one that does not decode or that your decoder drops) starts the count
  again. A 204 from the server, an error status and a cancel end the stream
  at once; the last item is always `SseDisconnected`, with the last event id
  and `retry`, so you can resume yourself.

## Your Dio is used as is

- Nothing on your `Dio` is changed: base URL, headers, timeouts,
  interceptors, transformer and `validateStatus` stay yours. Nothing is
  retried: that is the job of your interceptors.
- Error statuses go through your interceptors' `onError` before they are
  typed.
- Every request carries its `OperationInfo` (operation id, method, path
  template, tags): `OperationInfo.of(options)` in an interceptor.
- The path and the query string are encoded by the runtime and passed to
  Dio as one path, so `options.queryParameters` is empty in interceptors;
  read `options.uri` instead. Dio collapses every `//` of the finished URL;
  when a query value holds `//` (an `allowReserved` value such as
  `next=/a//b`) and the base URL is absolute, the runtime joins the base URL
  itself so the value is kept.

## Notes

- `Result` has the same name as `Result` in `package:async`. In a library
  that imports both, hide one (`import 'package:async/async.dart' hide
  Result;`, or `import 'package:typed_openapi_runtime/typed_openapi_runtime.dart'
  hide Result;`) or import one with a prefix.
- JSON is parsed by Dio. When the body is not valid JSON, Dio drops the
  response, so the `DecodeError` has no `statusCode`, and its `rawBody` is
  the text Dio's parser reported: the whole body when Dio read it at once,
  only the failing chunk when Dio streamed it (a `Content-Length` header was
  present). When compiled to JavaScript, Dio reports only the browser's
  `SyntaxError` message, so `rawBody` is `null` there.
- A `FormatException` thrown while decoding (your converter, `Date.parse`)
  is a data problem: a `DecodeError` in a result, an `SseDecodeError` in an
  event stream. An `Error` is a bug and is not caught.
- A path parameter whose expansion is empty or a dot segment (`''`, an empty
  list, a `label` of `''`) throws `ArgumentError`: the client would drop the
  segment, so `/users/{id}/sessions` could become `/users/sessions`.
- `rawBody` of a `DecodeError` and of an `UndocumentedStatus` is best-effort:
  it is the body as Dio returned it (parsed JSON, text or bytes), and `null`
  when the response had no body or Dio kept nothing.
- A `date-time` must be RFC 3339 with an offset (`2024-02-03T04:05:06Z`). A
  value without an offset is a `DecodeError` with a hint: for a server that
  sends another format, map the format to your own type with a converter
  (`types.formats`) or override the property's `format`. A `date` must be
  `YYYY-MM-DD`; a date-time sent for it is a `DecodeError` as well.
- Integers beyond 2^53 lose precision on the web, where `int` is a
  JavaScript number. If the API has such ids, map the property to your own
  type with a converter (`types.formats` or a `dartType` override, R6.8),
  such as `BigInt` or `String`: `JsonReader.asString` rejects a JSON number.

## Web

The package works on the web, compiled to JavaScript (dart2js) or to
WebAssembly (dart2wasm). Event streams need a streaming adapter there: Dio's
default browser adapter delivers a body only when the connection closes, so
an event-stream operation returns a `TransportError` that says so
(`DioRequestSender.webStreamingMessage`). Set a fetch-based adapter on your
Dio, such as `ConversionLayerAdapter` from `dio_compatibility_layer` with
`package:http`'s `BrowserClient` or `fetch_client`. A reconnection sends
`Last-Event-ID`, which is not a CORS-safelisted request header: for a
cross-origin stream the server must allow `Last-Event-ID` in
`Access-Control-Allow-Headers` in its preflight answer, or every reconnection
that carries an id fails with a `TransportError`.

Browsers do not let a page set the `Cookie` request header, so cookie
parameters do not work on the web (the browser keeps its own cookies and
sends them itself, subject to its credentials settings). A test checks it
in Chrome, compiled to JavaScript and to Wasm: a `Cookie` header set
through Dio, by a cookie parameter or directly, never reaches the server,
while the other headers of the same request do.

## Development

```sh
dart test                                    # the VM
dart test -p chrome                          # dart2js (needs Chrome)
dart test -p chrome --compiler dart2wasm     # dart2wasm
```

Test files and tests that need the VM (`dart:io`, int64 literals) are marked
`@TestOn('vm')` or `testOn: 'vm'`; `test/dio/web_test.dart` runs in a browser
only. If Chrome is not found, set `CHROME_EXECUTABLE`.
