# typed_openapi

Генератор Dart-клієнтів з OpenAPI 3.x для неідеальних специфікацій, згенерованих з коду.

> **Статус:** рання стадія проєктування, пакет ще не опубліковано.

- Вхід: локальний файл OpenAPI 3.0 / 3.1 / 3.2 (JSON або YAML).
- Вихід: готовий Dart-код на Dio, без кроку `build_runner`.
- Моделі дотримуються контракту `json_serializable` (`fromJson` / `toJson`).
- Дефекти специфікації виправляються іменованими правилами нормалізатора і
  потрапляють у звіт як діагностика зі стабільними кодами. Усе неоднозначне
  супроводжується пропозицією override-у.

## Використання

Опиши кожен клієнт у `typed_openapi.yaml` поряд із `pubspec.yaml`:

```yaml
defaults:
  preset: nestjs          # пресет нормалізатора; також: generic, fastapi, springdoc, aspnet
clients:
  core_api:
    input: specs/core_api.json      # локальний знімок, JSON або YAML
    output: lib/src/api/core_api    # у кожного клієнта свій каталог
```

Перевір специфікації без генерації:

```sh
dart run typed_openapi check            # усі клієнти
dart run typed_openapi check core_api   # один клієнт
dart run typed_openapi check --format json   # також: sarif, github-actions
```

Згенеруй клієнти, у яких перевірка не знайшла помилок (клієнт з
помилками пропускається, а код виходу такий, як у `check`):

```sh
dart run typed_openapi generate          # усі клієнти
dart run typed_openapi generate core_api # один клієнт
dart run typed_openapi generate --force  # замінити й файли, яких він не писав
dart run typed_openapi generate --break-lock  # забрати замок невідомого власника
```

### Що пише `generate`

Кожен клієнт отримує таке дерево у своєму каталозі `output`:

```text
<output>/
  petstore.dart          кореневий клас; експортує models.dart і api.dart
                         (api_client.dart для клієнта api чи models)
  api.dart               експортує файли груп
  api/pets_api.dart      звичайний клас на групу (тег)
  models.dart            експортує всі моделі
  models/pet.dart        по файлу на клас
  .typed_openapi.json    маніфест
```

Кожен Dart-файл має заголовок `// GENERATED CODE - DO NOT MODIFY BY HAND.` і
`// dart format off` у другому рядку. Код чистий під `package:lints/recommended` і правилами `flutter_lints`
без `ignore_for_file`, а та сама специфікація з тим самим конфігом дає ті самі
байти. Класи — звичайні `class` (не `final`, тож їх можна розширювати); база
union — `sealed`.

- Моделі мають `fromJson(Map<String, Object?>)` і `toJson()`, `==`,
  `hashCode` та `toString`. `fromJson` кидає `JsonDecodeException` з pointer-ом
  першої властивості, що не збігається. Властивість, якої схема не перелічує,
  потрапляє в `additionalProperties`, якщо схема це дозволяє. `date` — це
  `Date` із runtime, `date-time` — `DateTime` (RFC 3339 зі зсувом), `byte` і
  `binary` — байти. Optional nullable властивість тіла PATCH — `Patch<T>?` за
  налаштуванням `tri_state`.
- Enum-и відкриті: відоме значення — `Status.active`, значення, якого
  специфікація не перелічує, — `StatusUnknown` із сирим значенням, і воно
  пишеться назад так, як прийшло.
- Union-и — `sealed`-класи з класом на варіант (`PetCat`) і невідомим
  варіантом (`PetUnknown`) із сирим JSON. З `discriminator` варіант обирає
  значення; модель, у якої немає для нього властивості, отримує його від
  обгортки зі значенням, з яким її декодовано (аліас на кшталт `kitty` для
  `cat` зберігається). Схема з дискримінатором, яку розширюють інші схеми
  через `allOf` (уся ієрархія, також в інших файлах, які читає специфікація),
  — це union цих моделей. Без дискримінатора варіанти розрізняються за
  JSON-типом; варіанти зі спільним типом (TOA453) стають одним варіантом, що
  зберігає сирий JSON, якщо не попросити генератор пробувати варіанти по
  черзі:

  ```yaml
  defaults:
    union: structural        # raw (типово) або structural; також у клієнті
  ```

  Той самий ключ — це override для однієї схеми чи властивості
  (`union: structural` під нею у файлі override-ів) і він сильніший за
  конфіг. Дискримінатор у джерелі кращий за обидва варіанти.
- Гілка enum або `const` поруч із простою гілкою того ж типу
  (`anyOf: [string, {enum: ['']}]`) не додає значень і відкидається (info
  `TOA455`); doc-коментар поля перелічує відкинуті значення як «Known
  values». Для `oneOf` це приймає значення, яке підходить обом гілкам (`''`),
  хоча `oneOf` зі специфікації його відхилив би; так задумано, бо ця ідіома
  означає «будь-що з цього».
- Секрет ніколи не друкується: `toString` пише `<redacted>` для властивості
  з `writeOnly` або `format: password` (також через `$ref`, nullable `anyOf`
  на кшталт `Optional[SecretStr]` у Pydantic, елементи масиву, значення map
  чи варіант union). Значення, що лишається сирим JSON (`JsonValue` або клас
  `...Unknown` union-а), теж друкується як `<redacted>`, якщо його схема може
  містити секрет: будь-яка модель чи варіант union-а, які воно може
  тримати, на будь-якій глибині має секретну властивість.

### Операції

Операції клієнта — у `api/<група>.dart`, звичайний клас на групу
(`PetsApi`), експортує їх `api.dart`; корінь `<клієнт>.dart` (`petstore.dart`,
`api_client.dart` для клієнта `api` чи `models`) експортує моделі й API і
містить кореневий клас:

```dart
final client = PetstoreClient(dio); // naming.client його перейменовує
switch (await client.pets.getPet(petId: 1)) {
  case Success(:final data):
    print(data.name);
  case HttpError(:final body):
    print(body.code);
  case Failure():
    print('інша помилка');
}
```

- Усі аргументи іменовані, обов'язкові — `required`, тіло — `body`, останній
  — `CallOptions? call` (cancel token, додаткові заголовки, прогрес, `extra`
  для інтерсепторів). Метод повертає `Future<Result<T, E>>` і не кидає
  винятків на відповідь: задокументована помилка — `HttpError` із
  декодованим тілом, інший статус — `UndocumentedStatus`, тіло, що не
  декодується, — `DecodeError`, збій мережі — `TransportError`, скасований
  виклик — `Cancelled`.
- `T` — єдине тіло успіху (`void` без тіла, `JsonValue`, коли 2xx не описано,
  TOA653) або sealed-тип, коли 2xx різні (`CreatePetResponseOk`,
  `...Created`). `E` — `Never` без задокументованих помилок, єдине тіло
  помилки або sealed-тип за статусом (`CreatePetErrorNotFound`,
  `...ClientError` для `4XX`, `...Other` для `default`). Текстові успіхи —
  `String`, бінарні — `Uint8List`; їхні JSON-тіла помилок теж декодуються.
- Тіла: JSON-моделі; форми з `encoding` специфікації; multipart-частини як
  клас (`UploadPhotoRequest`), де бінарні властивості — `FileUpload`
  (`FileUpload.bytes`, що працює й у вебі, або `FileUpload.stream`, який
  браузерний адаптер Dio буферизує); частини йдуть у порядку схеми, тому
  текстова частина після файлу чи типізованої частини має
  `Content-Type: text/plain; charset=utf-8` (перед ними — без нього); частина,
  чий `encoding` називає список чи шаблон медіатипів, іде з одним конкретним
  типом (TOA661), а об'єктна частина не в JSON — це `String`, яку даєш ти
  (TOA662); бінарне тіло — `FileUpload`.
- Потоки подій (`text/event-stream`): метод повертає
  `Future<Result<Stream<SseItem<T>>, E>>`. Потік відкривається лише для
  задокументованого успіху (інший статус декодується як вище), дає
  `SseEvent` з декодованими даними (`T` — тип схеми, елемент схеми-масиву,
  `contentSchema` поля `data` з `itemSchema` OpenAPI 3.2 або `String` для
  тексту), `SseDecodeError` для події, що не декодується, і закінчується
  `SseDisconnected`; помилок потік не видає. Операція, що дає JSON і потік
  подій, має два методи: `chat` і `chatStream` (`naming.stream_suffix`).
  Перепідключення вимкнене: GET перепідключається, коли передаєш
  `CallOptions(sse: SseOptions(reconnect: true))` або з `sse: {reconnect:
  true}` у конфігу, надсилає `Last-Event-ID` і сповіщає кожну спробу через
  `SseReconnecting`; затримка — `retry` сервера, інакше 1 с, подвоюється до
  30 с, 5 спроб. POST не перепідключається. У вебі підключи до свого Dio
  адаптер на fetch: стандартний не вміє потоків.
- Події, типізовані поодинці (`itemSchema` OpenAPI 3.2, чиї гілки `oneOf`
  фіксують `event` константою), — sealed-union за назвою події:
  `ChatEvent` з `ChatEventDelta(data)`, `ChatEventDone()` і
  `ChatEventUnknown(event, data)`, тож `switch` називає кожну подію.
  Override `sse` операції задає те, чого не каже специфікація:

  ```yaml
  operations:
    createChat:
      sse:
        data: ChatChunk          # один тип для всіх подій, або:
        events: {delta: ChatDelta, done: null}   # тип на назву події
        unknown: ignore          # відкидати невідомі події (типово: keep)
        reconnect: true          # перепідключатися типово, також для POST
        method: only             # лише метод потоку (stream | only | none)
  ```
- Клієнт не змінює твій Dio: base URL задаєш ти, з констант серверів
  кореневого класу (`PetstoreClient.server`, або метод на кшталт
  `PetstoreClient.server1(region: 'eu')` для URL зі змінними). Коли query
  містить `//` (значення з `allowReserved`), а base URL абсолютний, runtime
  з'єднує їх сам, бо Dio схлопнув би `//`; відносний base URL лишається Dio,
  який `//` схлопує.
- Кожен запит несе `OperationInfo` у `RequestOptions.extra`
  (`OperationInfo.of(options)`): `operationId`, теги й вимоги безпеки з їхніми
  схемами, для інтерсептора, що додає облікові дані.

`generate` пише каталог виходу цілим. Він будує нове дерево і маніфест
(`.typed_openapi.json`: генератор, формат маніфесту, хеш входів і хеш кожного
файлу) поруч із виходом і підміняє ним старий каталог, тож невдалий запуск
лишає попередній вихід (або нічого), а не половину дерева. Запуск, що нічого
б не змінив, каталогу не торкається.

Вихід, написаний генератором лише моделей (до операцій), оновлюється на місці:
наступний запуск пише файли API і лишає моделі, без `--force`. Ваш власний
файл у ньому з іменем, яке тепер використовує повний клієнт (`api.dart`,
`<клієнт>.dart`, у будь-якому регістрі), відхиляється з `TOA830`, як і будь-який
інший чужий файл.

**Він замінює лише те, що сам написав.** Файл, який перелічено в попередньому
маніфесті й чий хеш досі збігається, замінюється чи видаляється. Будь-який
інший файл у каталозі — чужий (ваш, іншого клієнта, іншого інструмента) або
змінений (згенерований файл, який хтось правив): клієнт не генерується, а
помилка `TOA830` називає файли й нічого не змінює. Приберіть їх або запустіть
`generate --force`, щоб їх замінити (рядок клієнта каже, скільки замінено, а
info `TOA833` називає кожен перезаписаний чи видалений файл).
Каталог з файлами й без власного маніфесту відхиляється так само, бо всі його
файли чужі; так само і каталог, чий маніфест не має хешу для файлу (записаний
до формату маніфесту 2): один раз передайте `--force`, і новий маніфест матиме
хеші. Файл, який уже містить те, що запуск запише, ніколи не заважає.

`--force` ніколи не замінює каталог, що містить `pubspec.yaml`, є `lib`
пакета, містить символічне посилання або файл, який читає будь-який клієнт
конфігу (конфіг, специфікацію, її `$ref`-файли, overrides чи baseline; також
через символічні й жорсткі посилання чи інший регістр літер): `TOA830`
лишається. Клієнти з вихідними каталогами, що перетинаються, пропускаються всі
(`TOA904`).

З одним виходом працює один запуск. Він тримає файл-замок
`.<output>.typed_openapi.lock`, створений поруч із виходом, у якому названо
його процес. Другий запуск на тому самому виході отримує `TOA831` і нічого не
змінює. Замок процесу, якого вже немає (на тому самому хості), забирається
(info `TOA832`). Коли typed_openapi не може визначити, чи процес працює (інший
хост, нечитний замок, Windows), видаліть файл-замок або запустіть
`generate --break-lock`, що забирає такий замок і не замінює жодного файлу;
`--force` замків не чіпає. Замок процесу, що працює, лишається зайнятим.
Каталог, у який не можна писати, — це теж `TOA831`.

Запуск, убитий під час підміни, лишає каталоги `.<output>.typed_openapi-*`
(після тире вісім літер чи цифр, `-old` для резервної копії; ці імена належать
генератору, не користуйтеся ними). Наступний запуск, під замком і перевіривши
вихід, як описано вище, повертає попередній вихід, якщо його немає, прибирає їх
і повідомляє про це (info `TOA832`); каталог, у якому є файл, що читає будь-який
клієнт, він не чіпає. TOA830-TOA833 і TOA904 не можна знизити.

`check` читає всю специфікацію, проходить її `$ref` (зокрема в інші локальні
файли) і повідомляє про невідомі ключі, значення неправильного типу, биті або
зациклені посилання і конструкції, яких немає в оголошеній версії OpenAPI.
Потім працює нормалізатор: іменовані правила виправляють дефекти, виправлення
яких випливає зі специфікації або з HTTP (`required: true` на властивості,
повторені значення enum, неоголошені path-параметри, `default` не того типу),
а про решту повідомляють, що змінити в джерелі. `preset` додає до цих підказок
рецепт для вашого фреймворку. Правило вимикається в клієнті або в `defaults`:

```yaml
defaults:
  rules: {dedupe-enum-values: false}
```

Те, чого нормалізатор знати не може, виправляє файл override-ів — без змін на
бекенді. Вкажи його в клієнті (`overrides: typed_openapi.overrides.yaml`) і
адресуй специфікацію операціями та схемами, а не pointer-ами:

```yaml
operations:
  getPet:                     # operationId або METHOD /path: 'GET /pets/{id}'
    parameters:
      id: {schema: {type: integer, format: int64}}   # path:id, якщо імена збігаються
    responses:
      '200': {contentType: application/json}
schemas:
  Pet:
    reason: бекенд надсилає null для тварин без власника
    properties:
      owner: {nullable: true}
      photo: {type: string, format: binary}
```

Override-и змінюють специфікацію до нормалізатора; `null` прибирає поле.
Override, ціль якого зникла, дає warning, той, з яким специфікація вже
збігається, — info, що його можна прибрати, а ключ з одруком — помилку з
підказкою найближчого відомого ключа. Поля для генератора (`name`, `exclude`,
`group`, `exhaustive`, `dartType`, `triState`, `union`) задають ім'я,
виключення, групу і тип того, що генерується. `group` пишеться в UpperCamelCase, як ім'я класу
(`pet-store` використовується як `PetStore`); `name` методу, аргументу чи
схеми має бути коректним іменем Dart, інакше `TOA560` каже, яке ім'я
використано натомість. Підказки правил, які не можуть виправити
дефект самі, закінчуються override-ом, який можна скопіювати.

`check` також визначає, що буде згенеровано: імена, групи і Dart-типи.
Колізії імен отримують суфікс (`List` -> `ListModel`, `class` -> `class_`,
`getPet2`) і info з override-ом, що закріплює ім'я. Що і як генерувати,
задається в `defaults` або для клієнта:

```yaml
defaults:
  naming:
    client: PetstoreClient       # кореневий клас; за замовчуванням ім'я клієнта + Client
    group: '{Tag}Api'            # клас на тег; group_by: tag|path|single
    patch_suffix: Patch          # PetPatch: тіло PATCH схеми, вжитої ще деінде
    operation_prefix: '^v1_'     # зрізається з operationId (nestjs: XController_)
  include: {tags: [pets], paths: ['/store/**']}
  exclude: {operations: [deletePet]}
  types:
    number: double               # number без формату; за замовчуванням num
    formats: {decimal: {type: Decimal, import: 'package:decimal/decimal.dart'}}
    schemas: {Money: {type: Money, import: 'package:app/money.dart', converter: MoneyConverter}}
  tri_state: patch               # optional nullable поля PATCH — Patch<T>?
  union: raw                     # union без дискримінатора, див. вище
  errors: {default_schema: ErrorDto}
```

Як працюють фільтри:

- `include` — об'єднання: операція генерується, якщо їй відповідає
  будь-який тег, `operationId` або шаблон шляху з `include`. Порожній
  `include` — це відсутність фільтра.
- `exclude` сильніший за `include`. Шаблон в обох — info `TOA558`, шаблон,
  що не збігається з жодною операцією, — warning `TOA557`.
- У шаблоні шляху `*` — один сегмент, `**` — будь-яка кількість сегментів,
  `?` — один символ. `/pets/*` збігається з `/pets/{id}` і не збігається з
  `/pets`; `/pets/**` теж не збігається з `/pets`, тож щоб узяти колекцію і
  все під нею, вкажи обидва.
- `operations` збігаються з `operationId` так, як його пише специфікація, до
  того як зрізано `operation_prefix` (із пресетом `nestjs` —
  `UsersController_findAll`, а не `findAll`). Префікс зрізається лише там,
  де його збіг починається з початку id і не порожній.
- Теги чутливі до регістру, операція збігається за будь-яким зі своїх тегів.

Ще `check` повідомляє замість того, щоб вгадувати: клієнт, що не генерує
жодної операції (усе відфільтровано, записано як `$ref` або шлях має
змінну без параметра), — warning `TOA563` з причиною; тіло з медіатипом, що
не JSON, не форма, не текст і не потік подій, надсилається і читається як
байти без своєї схеми (info `TOA650`; інші медіатипи операції, що
відкинуто, — info `TOA651`); `errors.default_schema`, якого немає серед
ключів `components.schemas`, — warning `TOA652`, налаштування ігнорується;
`style` параметра, який його `in` не дозволяє (path `form`, query `matrix`,
...), — warning `TOA564`, береться style за замовчуванням, а параметр
`in: querystring` (OpenAPI 3.2) — warning `TOA565`, він не генерується. Параметри
заголовків `Accept`, `Content-Type` і `Authorization` не генеруються: OpenAPI
каже їх ігнорувати.

У кожної знахідки є стабільний код (`TOA011`), JSON-pointer на місце в
специфікації і, якщо парсер зміг визначити позицію, рядок і колонка. Шляхи —
відносно каталогу, з якого запущено команду. Рівень коду (за кодом або
назвою) змінюється в `defaults` або в клієнті; `off` вимикає його. Коди про
те, що файл специфікації, override-ів чи baseline не читається, і коди
`generate` (TOA830-TOA833) знизити не можна:

```yaml
defaults:
  severity: {TOA208: off, duplicate-operation-id: warning}
```

Щоб почати зі специфікацією, де багато знахідок, зафіксуй наявні в baseline
і вали перевірку лише на нових:

```yaml
clients:
  core_api:
    input: specs/core_api.json
    output: lib/src/api/core_api
    baseline: specs/core_api.baseline.yaml
```

```sh
dart run typed_openapi baseline create   # зафіксувати сьогоднішні error і warning
dart run typed_openapi check             # лише нові; «baselined: N»
dart run typed_openapi check --show-baselined
dart run typed_openapi baseline prune    # прибрати записи, що вже не збігаються
```

Знахідка зіставляється за fingerprint її коду і місця (операція, параметр,
схема чи властивість, якщо місце їх має), а не за текстом чи рядком, тож
інше формулювання повідомлення чи правка деінде в специфікації його не
змінюють. Запис, що більше не збігається, — warning з підказкою
`baseline prune`; `check --strict-baseline` робить його помилкою за будь-якого
рівня з конфігу. `check` повідомляє `TOA820` (baseline-файл не існує), доки
перший `baseline create` його не запише. `baseline create` і `baseline prune`
не чіпають baseline клієнта, чию специфікацію не вдалося прочитати, і
завершуються з кодом `1`. Код виходу `1` означає хоча б одну незафіксовану
помилку, `64` — неправильні аргументи або невідомий клієнт, `78` — конфіг не
вдалося прочитати.

`--format github-actions` друкує по одній анотації workflow на знахідку;
GitHub показує лише обмежену кількість анотацій за запуск, тож для
специфікації з багатьма знахідками спершу заведи baseline.
